# IdmCCNOBackend local Docker environment

Prerequisites: Rancher Desktop 1.24.0 with container engine Moby/dockerd, Docker CLI, and Docker Compose.

```powershell
docker compose up -d --build
docker compose ps
docker compose logs -f idmccnobackend
docker compose down
```

`docker compose down -v` also deletes the local MySQL volume (`mysql-data`) and is intentionally left as an explicit, opt-in reset command — omit `-v` to keep existing data across restarts.

The application uses the `container` Spring profile and connects to the Compose service named `mysql` (container-to-container traffic uses service names, never `localhost` — see `compose.yml`). Credentials in `compose.yml` are local-only development values.

## Services

| Service | Image | Windows port | Notes |
|---|---|---|---|
| `mysql` | `mysql:8.4.5` | none (internal only) | Schema `spesaadomicilio` for app data (`CCNO_*`/`sd_coop_*`); separate `keycloak` schema for Keycloak's own tables |
| `keycloak` | `quay.io/keycloak/keycloak:26.6.4` | `8081` → 8080 | Uses the imported Keycloak dump in schema `keycloak` |
| `idmccnobackend` | built from `Containerfile` (JDK 25) | `8080` → 8080 | Spring Boot executable jar, root context path `/` |

## Database: importing a real dump

Without a dump in `DB/local/`, both schemas stay empty (`spring.jpa.hibernate.ddl-auto` is `none` in `application-container.yml`, matching production) — `idmccnobackend`'s `CCNO_*` tables won't exist and back-office login will fail. For a schema-only (no real data) run, pass `-e SPRING_JPA_HIBERNATE_DDL_AUTO=update` to the `idmccnobackend` service instead.

To import real data:

1. Copy the application dump into `DB/local/data/01-dump.sql` and the Keycloak dump into `DB/local/keycloak/01-keycloak.sql` (the whole `DB/local/` tree is gitignored — never commit it, production dumps typically contain real customer PII):
   ```powershell
   New-Item -ItemType Directory -Force .\DB\local\data | Out-Null
   New-Item -ItemType Directory -Force .\DB\local\keycloak | Out-Null
   Copy-Item "<path to app dump>.sql" .\DB\local\data\01-dump.sql
   Copy-Item "<path to keycloak dump>.sql" .\DB\local\keycloak\01-keycloak.sql
   ```
2. Start from a clean volume so MySQL runs the init scripts (they only run once, on an empty data directory):
   ```powershell
   docker compose down -v
   docker compose up -d --build
   ```
   MySQL runs, in order: `00-create-keycloak-db.sql` (creates the `keycloak` schema), `01-import-dump.sh` (imports `DB/local/data/01-dump.sql` into `spesaadomicilio` with `mysql --force`), `02-import-keycloak-dump.sh` (imports `DB/local/keycloak/01-keycloak.sql` into `keycloak`), `02-rename-app-tables.sql` (renames app `CCNO_*` tables to the lowercase names generated by Hibernate).
   A large dump can take a while to import on first boot — watch `docker compose logs -f mysql` until it reports "ready for connections" a second time (end of the init script phase).
3. Keycloak 26 starts against the imported `keycloak` schema and performs any pending schema validation/migration on startup.

### Testing a real login through Keycloak

```powershell
curl -X POST http://localhost:8081/realms/IdmCCNO/protocol/openid-connect/token `
  -d grant_type=password -d client_id=idmccno-test-client `
  -d username=<test-username> -d password=<test-password>
```

A JSON response containing `access_token` confirms Keycloak itself works end-to-end. Note: `idmccnobackend`'s own back-office login (`/login`) is session-based against the local `ccno_be_user` table (BCrypt) and does **not** validate Keycloak Bearer tokens — `idmccnobackend` only depends on Keycloak for its health check (`/actuator/health`) and for read-only queries against Keycloak's `USER_ENTITY`/`USER_ATTRIBUTE` tables (imported as part of the app dump, in the `spesaadomicilio` schema, independent of the live `keycloak` schema).

The health endpoint is `http://localhost:8080/actuator/health`.
